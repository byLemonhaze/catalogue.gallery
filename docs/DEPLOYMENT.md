# Deployment Notes (Cloudflare Pages + Functions)

## Scope

This runbook covers:

- Wrangler setup/authentication
- Cloudflare bindings/secrets for this repo
- environment model (local, preview, production)
- migration and deploy sequence

## 1) Prerequisites

- Node 22+
- npm
- Cloudflare account access to the target Pages project
- Sanity project access (read/write token)
- Resend API access

## 2) Wrangler Setup

1. Install dependencies:
   - `npm install`
2. Authenticate Cloudflare CLI:
   - `npx wrangler whoami`
   - If unauthenticated: `npx wrangler login`

## 3) Bindings and Config

Current Cloudflare config lives in [`wrangler.toml`](../wrangler.toml):

- `pages_build_output_dir = "dist"`
- D1 binding:
  - `binding = "CONTACTS_DB"`
  - `database_name = "catalogue-private-contacts"`

The runtime expects `CONTACTS_DB` to exist in both preview and production.

## 4) Environment Model

### Local

- Use `.env.local` (copied from `.env.example`) for local development.
- Never commit `.env` or `.env.local`.

### Cloudflare Preview + Production

Set the following environment variables/secrets in Cloudflare Pages for both environments:

- `VITE_SANITY_PROJECT_ID`
- `VITE_SANITY_DATASET`
- `SANITY_WRITE_TOKEN`
- `RESEND_API_KEY`
- `RESEND_FROM_EMAIL`
- `RESEND_REPLY_TO`
- `PUBLIC_BASE_URL`
- `VITE_CF_WEB_ANALYTICS_TOKEN` (optional, only if using manual beacon injection)
- `WEBHOOK_SHARED_SECRET`
- `EMAIL_ENCRYPTION_KEY`

The above config supports the public site and applications/review. `CONTENT_LAB_PASSWORD`, `GROK_API_KEY` and `CLAUDE_API_KEY` are **legacy editor dependencies**, not prerequisites for reading bot-published content. Existing legacy code still references them; consult [the inventory](legacy/CONTENT-LAB.md) before changing or revoking any secrets. External Grok bot credentials are configured in the bot environment, outside this repo.

Environment-specific behavior for social metadata:

- Production: set `PUBLIC_BASE_URL=https://catalogue.gallery`.
- Canonical URLs always use `https://catalogue.gallery`. Global middleware adds noindex to other `*.pages.dev` hosts, including static/error responses; production aliases redirect to the canonical host. Verify actual deployed headers. See [SEO delivery](./SEO.md).

## 5) D1 Provisioning and Migrations

If the D1 database is not already created:

1. `npx wrangler d1 create catalogue-private-contacts`
2. Update `database_id` in `wrangler.toml`

Application/review schema migrations (apply in order for a new database; preserve existing data):

1. `npx wrangler d1 execute catalogue-private-contacts --remote --file=./migrations/001_submission_contacts.sql`
2. `npx wrangler d1 execute catalogue-private-contacts --remote --file=./migrations/002_contact_notifications.sql`

`migrations/003_content_drafts.sql` belongs to the retained legacy editor. It is not needed by external bot → Sanity publishing. Preserve an existing `content_drafts` table; any retirement or new legacy-editor provisioning is a separate reviewed operation.

## 6) Build and Deploy Sequence

### Pre-deploy checks (required)

1. `npm run verify` (lint, typecheck, tests)
2. `npm run build` (client, SSR, SEO generation and local share audit)
3. `npm run audit:shares -- --remote` (remote image checks)

### Deploy

The existing `catalogue` Pages project (`artfinder.pages.dev`, custom domain `catalogue.gallery`) uses direct uploads; it has no Git provider connected as verified on 29 September 2026. A GitHub merge does not deploy production automatically.

1. Merge the approved PR into `main` after the required GitHub check passes.
2. Build the merged commit with `npm run build` and the production public CMS settings.
3. Verify Cloudflare authentication with `npx wrangler whoami`.
4. From the repo root, run `npx wrangler pages deploy dist --project-name catalogue --branch production --commit-hash <merged-commit-sha>`. Cloudflare’s configured production branch is named `production`; `main` uploads are previews. The source commit still comes from GitHub `main`. Running from the root includes Pages Functions in `/functions` and the existing D1 binding from `wrangler.toml`.
5. Confirm the deployment is production, then check `https://catalogue.gallery`, artist/article routes, API availability, and asset/HTML caching headers.

PR branches can be uploaded explicitly as Cloudflare previews when needed. They are not deployed automatically.

### Preview Links (for social QA)

Use the actual Cloudflare deployment URL returned by Wrangler when validating social embeds.

Checklist:

1. Open the preview URL generated by Cloudflare Pages for that branch.
2. Share/test from that exact URL (not production).
3. Verify canonical and social page URLs use the production origin. Confirm preview indexing is blocked on dynamic, static and error responses by the global middleware described in SEO.md. Noindex is not access control.

## 7) Cloudflare Analytics and Error Tracking

### Web Analytics (Dashboard)

Web Analytics is enabled in Cloudflare Dashboard, not by `wrangler.toml`.

1. Cloudflare Dashboard → **Web Analytics** → Add/select `catalogue.gallery`.
2. For proxied production hostname: use automatic injection (`Enable`).
3. For preview/testing or manual mode: set `VITE_CF_WEB_ANALYTICS_TOKEN` and keep SPA mode enabled.
4. Verify in DevTools network:
   - `https://static.cloudflareinsights.com/beacon.min.js`
   - requests to `cloudflareinsights.com`

### Basic Error Tracking

- Browser runtime errors are sent to `POST /api/client-errors`.
- Function logs structured events to Cloudflare logs (`[client-error] ...`).
- View logs:
  - `npx wrangler pages deployment tail --project-name <project-name>`
  - or Cloudflare dashboard log stream.

## 8) Webhook Setup

In Sanity webhook settings:

- URL: `https://<your-domain>/api/webhook`
- Trigger: artist/gallery create/update events relevant to review status
- Secret/header must match `WEBHOOK_SHARED_SECRET`

## 9) Rollback Strategy

- Pages rollback: promote/redeploy last known-good deployment in Cloudflare dashboard.
- D1 rollback: ship a forward SQL migration that repairs bad state (avoid ad-hoc production edits).
- Secrets rollback: revert changed secret values in Cloudflare env settings and redeploy.

## 11) Editorial selection and asset caching

- Build/validate Studio locally with `cd studio && npm ci && npm run build`. Deploying Studio is a separate authorized operation. The frontend works with stable defaults before the schema or a selection document is published.
- In Studio, create one **Homepage editorial selection** document. Choose an optional lead and up to four ordered story references for **Worth returning to**. Keep original publication dates. If multiple selection documents exist, the most recently updated published one wins.
- Public server rendering reads Sanity's origin API; browser fallback reads use the CDN. Public HTML has a five-minute cache window, and already-open tabs retain their snapshot until reloaded. Ordinary new Stories/Dispatch documents need no frontend deployment. See [Editorial publishing](EDITORIAL-PUBLISHING.md) for date gates and historical fallback caveats.
- `/assets/*` receives one-year immutable caching because Vite fingerprints those filenames. HTML and generated profile metadata do not receive this policy.
- A stale lazy import triggers at most one automatic reload per minute; subsequent failures show a manual retry screen. This handles stale lazy chunks after a Pages deployment but cannot recover an entry script that fails before React starts. Keep HTML revalidated and verify old-tab navigation across deployments.
- For local visual review, run `npm run build` then `npm run preview -- --host 127.0.0.1 --port 4173`. This reads public CMS content through a local GET-only proxy. Vite preview does not emulate Pages Functions, Cloudflare headers, or edge caching.

The frontend build also creates `server-dist/entry-server.js`, which Pages Functions import. ## Aligned release from a protected main branch

`main` is protected: changes must pass through a pull request and the required **Lint, type check, test, build** status check. Do not push directly to main, bypass checks, force-reset local work, or deploy a feature branch as production.

1. Commit the reviewed source, documentation and evidence on a feature branch. Push it, create the PR, then wait for its checks to register and pass. Use a PR description for the actual change; checked-in earlier PR bodies are historical evidence.
2. Squash-merge the checked PR. Switch to local main, fetch origin and pull with `--ff-only`. If this fails, stop and inspect divergence; do not discard local commits.
3. Require a clean working tree and identical `HEAD` and freshly fetched `origin/main`. Run the **complete** `npm run build`, including SEO generation. An npm/network failure after the client/SSR bundle still means the overall build failed.
4. From the repository root, deploy with `npx wrangler pages deploy dist --project-name catalogue --branch production --commit-hash "$(git rev-parse HEAD)"`. Keep `functions/`, `server-dist/` and `wrangler.toml` present. This Pages project uses direct uploads; merging GitHub main alone does not publish it.
5. Inspect `npx wrangler pages deployment list --project-name catalogue`. Confirm the latest successful **Production** deployment identifies the merged commit. Check `https://catalogue.gallery/`, a directory/profile/world route, a Dispatch edition and a story. Include the homepage Counterpoint transcript and its edition link in the smoke checks.
6. Fetch origin again and compare local main, origin/main and the deployment commit. If another change reached main during the release, alignment has not been achieved: build/deploy the new reviewed main or coordinate the concurrent release.

Record the PR URL, merge SHA, deployment ID/URL, successful production status and live smoke checks in the PR release comment. This preserves the post-deployment evidence without creating another source commit that immediately makes the deployed SHA stale. Do not report full alignment until those facts are observed.
